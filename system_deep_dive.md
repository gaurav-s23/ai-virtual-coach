## 1. SYSTEM OVERVIEW

This platform solves a practical hiring-preparation problem: candidates need repeated, realistic practice across technical interviews, aptitude-style mock tests, and English communication sessions, but most tools either provide static question banks or expensive one-off coaching. The system addresses that gap with a production-oriented loop that combines structured application workflows with AI generation and resilient backend controls.

The primary users are candidates preparing for software and technical roles, and platform administrators who monitor usage, quality, and system health. Candidates use three core modes. Interview mode is personalized using resume-derived context and dynamic follow-up behavior. Mock mode provides globally shared question sets to reduce generation cost and improve consistency across users. English mode provides topic-driven speaking practice and a report-based feedback cycle.

The platform is needed because practice quality and operational reliability must coexist. AI-only prototypes often fail under latency, provider instability, or state-loss events. This system is designed to preserve user continuity under those conditions while keeping generation quality acceptable through retries, schema validation, and deterministic fallback responses.

## 2. ARCHITECTURE DECISIONS (VERY IMPORTANT)

FastAPI was selected because the backend is I/O-heavy and failure-sensitive. The interview and report flows depend on upstream AI providers and asynchronous processing; FastAPI’s async model is a better fit than synchronous Flask for throughput under waiting workloads. Compared with a Node backend, Python provides more direct alignment with AI and RAG libraries used here (LangChain, sentence-transformers, vector integrations), reducing integration friction and operational complexity.

PostgreSQL is used as the primary state store because the system requires strong consistency for user sessions, global mock replacement, token and auth records, and durable status tracking. Document stores could simplify some JSON payload handling, but transaction semantics and predictable locking behavior are critical for race-sensitive operations such as global mock replacement.

Redis is optional by design. It accelerates cache reads and reduces repetitive LLM calls, but the system cannot depend on it for correctness. Redis is treated as a performance layer rather than a state authority, which allows graceful degradation when Redis is unavailable.

The RAG pipeline exists because fully prompt-only interview generation quickly becomes generic. Resume extraction plus embedding improves relevance without requiring full-document token transfer on every call. The trade-off is additional compute and queue management complexity, which is mitigated through asynchronous processing and persistent status tracking.

An explicit LLM abstraction (`llm_service`) is a deliberate boundary. It centralizes prompt shaping, timeout control, retry policy, schema validation, and cache strategy. Without this layer, route handlers tend to duplicate error-prone logic and diverge in behavior over time.

## 3. HIGH-LEVEL ARCHITECTURE

The React frontend is workflow-oriented: setup and input capture happen client-side, while generation and session updates happen server-side via authenticated API calls. The FastAPI backend is modular, with routes handling transport concerns and services handling business logic. PostgreSQL stores durable state for users, interview sessions, RAG status, global mocks, and DB cache fallback entries. Redis, when configured, serves as a fast cache tier. The AI layer consists of LLM provider access through LiteLLM plus the RAG embedding/retrieval subsystem.

Interactions are request/response for user actions and queued background processing for heavy embedding tasks. This hybrid model keeps user-facing latency low while preserving eventual enrichment of context through asynchronous RAG completion.

## 4. COMPLETE DATA FLOW (CRITICAL)

### Interview Flow (DETAILED)

The flow starts when the user enters name, role, JD text, and resume. Name is required because personalization and transcript traceability are operational requirements, not cosmetic enhancements; it is persisted with the interview record. Resume upload is validated for basic integrity and size limits before any expensive processing begins. This guards both cost and abuse risk.

RAG processing begins asynchronously through the queue-style task manager in `rag_service`. Async is used so interview start does not block on embedding latency, which can vary by document complexity and model warm state. The trade-off is that early turns may run before full RAG readiness, so the system exposes and persists status (`processing`, `ready`, `failed`) and allows graceful operation even when enrichment is delayed.

Interview start returns quickly with an initial plan generated by `llm_service`. Inputs are intentionally truncated (`resume[:800]`, `jd[:400]`) to cap latency and token usage. This reduces completeness but improves predictability. The chat loop then validates session existence, produces feedback through schema-validated LLM output, and appends transcript turns in DB. Session persistence in DB—not memory—ensures continuity across restarts and multi-instance deployments.

Final reporting uses the same LLM service path: strict timeout, retries, schema validation, and fallback. Even under provider instability, the endpoint returns a valid report contract.

### Mock Flow (DETAILED)

Mock mode uses a global shared set because generating custom MCQs per user is expensive and rarely improves quality proportionally. A shared active mock provides consistency for benchmarking and materially reduces provider cost. When a forced refresh is requested, generation occurs once and replacement is performed atomically under transaction and advisory lock protection, guaranteeing single-writer behavior even under concurrent requests.

Caching reduces repeated generation calls. If Redis is healthy, cache reads are fast. If Redis fails, DB cache fallback preserves behavior and avoids crash paths.

### English Flow (DETAILED)

English flow is lightweight by design: topic selection, question generation, response capture, and report generation. It reuses the same resilient LLM pathway and therefore inherits retry, timeout, schema validation, and fallback controls. This keeps the mode reliable without introducing a separate orchestration stack.

## 5. FAILURE & FALLBACK DESIGN (VERY IMPORTANT)

The failure model is explicit. LLM calls run with strict timeouts and multi-attempt retries; if all attempts fail or schema parsing fails, fallback payloads are returned so API contracts remain stable. Redis is opportunistic: failures are logged and request handling continues through DB cache fallback. Session validation is enforced before chat/history actions, and missing sessions return `Session expired` rather than generic failures. DB failures surface as safe server errors and are logged with enough context for debugging.

```text
User -> Backend -> LLM
                 |
                 v (timeout/error)
               retry (bounded)
                 |
                 v
             fallback payload
                 |
                 v
           stable API response
```

## 6. STATE MANAGEMENT DESIGN

In-memory state is intentionally avoided for correctness-critical workflows. Interview state, transcript progression, and current question indexes are persisted in PostgreSQL. RAG processing status is persisted per user in `rag_status`, making progress visible and restart-safe. Caching follows a layered strategy: process memory for fastest short-lived hits, Redis for shared low-latency cache, and DB cache fallback for resilience when Redis is unavailable.

This design prioritizes continuity over absolute speed. The system remains functional under partial infrastructure degradation.

## 7. DATABASE DESIGN

`users` stores identity, authentication references, and dashboard counters. `interviews` is the operational source of truth for interview lifecycle: session key, candidate name, status, transcript, and context snapshot. `global_mocks` holds the active shared mock question set; it is intentionally singular in usage semantics. `rag_status` tracks async embedding state per user. `cache_entries` stores serialized cache fallback values with TTL metadata for degraded-mode continuity.

Each table exists to support a specific reliability concern: identity trust, session durability, controlled shared content, async observability, and cache resilience.

## 8. AI SYSTEM DESIGN

Prompts are structured with explicit output schema declarations and constrained context windows. Resume and JD truncation are deliberate latency and token controls, not arbitrary limits. The system favors predictable bounded generation over unconstrained completeness, then compensates with RAG enrichment over time.

Resume use is section-aware. Skills, experience, and projects are extracted and stored with metadata before chunking. This increases retrieval precision compared with raw full-text chunking and supports better follow-up relevance.

Schema validation uses pydantic models after JSON parse attempts. Invalid or malformed outputs do not propagate to routes; they are treated as generation failure and replaced with deterministic fallback payloads.

Fallback is mandatory because provider-side instability is a certainty in production. The system guarantees valid response shapes even during outages.

## 9. PERFORMANCE DESIGN

Performance control is built around non-blocking and reuse. RAG embedding is queued and processed in workers, so interview start stays responsive. LLM calls are reduced through hierarchical caching and shared global mock design. Repeated resume parsing is minimized by storing contextual summaries in session records and embedding durable vectors once per update path.

Blocking operations are pushed either to async provider calls or queue workers. This keeps p95 latency under control for user-facing endpoints.

## 10. SECURITY DESIGN

JWT-based auth protects user APIs, and role-based tokens protect admin APIs. Admin credentials are sourced from environment variables and validated at startup to avoid latent runtime misconfiguration. Secret hygiene is treated as operational risk: missing or invalid critical secrets fail fast at boot.

The largest security risk remains key exposure through poor deployment hygiene, not application logic itself. The architecture assumes environment isolation and secret rotation practices are in place.

## 11. EDGE CASE HANDLING

Empty or undersized resume uploads are rejected early. Oversized files are blocked with validation errors. Invalid or text-poor PDFs can still allow interview start, but RAG status may end in `failed`; this is visible and does not crash interview flow. LLM failures trigger retry and fallback, preserving response contracts. User disconnects during interaction do not corrupt persisted transcripts because writes are turn-based. Session expiry or invalid session IDs return explicit session-expired responses.

## 12. SCALABILITY CONSIDERATIONS

At around 100 concurrent active users, the current architecture remains practical with tuned worker counts, caching, and DB connection management. At 1000+ concurrent users, stress points emerge around embedding throughput, provider quotas, and DB lock/contention around shared resources. Redis becomes more important at that scale, and queue isolation becomes mandatory.

To scale beyond current bounds, dedicated queue workers, stronger observability, and autoscaling policies are required. The current design is resilient-first but not infinite-throughput by default.

## 13. LIMITATIONS (BE HONEST)

The queue implementation is lightweight and process-coupled, not a fully externalized job system. Advisory lock logic is strongest on Postgres and weaker on non-Postgres engines. LLM quality remains provider-dependent despite retries and schema checks. Fallback responses preserve availability but can reduce response richness under sustained provider failure. Cache invalidation strategy is TTL-based and does not yet support fine-grained domain-aware invalidation.

## 14. FUTURE IMPROVEMENTS

Already implemented improvements include queue-style RAG processing with retry, DB-backed RAG status, transactional global mock replacement with advisory locking, startup dependency and env validation, Redis-to-DB cache fallback, and structured operational logging across key flows.

Remaining improvements include migration to a fully external queue system (Celery/RQ), richer retrieval ranking and section scoring in RAG, lock abstraction for multi-database portability, end-to-end metrics dashboards, and automated load-shedding strategies under upstream provider saturation.

## 15. RESILIENCE DESIGN

Resilience is designed as graceful degradation rather than binary success/failure. Under LLM provider instability, bounded retries plus fallback payloads keep APIs live. Under Redis failures, cache reads/writes degrade to DB-backed fallback and in-memory local cache without request crashes. Under DB problems, safe error responses are returned and errors are logged with request context. Under high request rates, endpoint-level rate limiting on chat and quiz paths reduces abuse and protects shared resources.

This layered resilience model ensures the platform can continue serving users in reduced mode while preserving data integrity.

## 16. OBSERVABILITY & MONITORING

The platform uses structured log events around critical operations: interview start, chat turn progression, pivot generation, mock generation/reuse, LLM fallback events, Redis cache failures, and background embedding retries. Request middleware adds request IDs and duration metrics for correlation. Debugging is performed by combining request-level logs with domain-level service logs to localize failures quickly.

Current observability is log-centric and suitable for operational debugging. The next maturity step is explicit metrics and tracing integration for SLO management and automated alerting.

## 2. ARCHITECTURE

- **Frontend**: React (Vite), route-based pages for setup/interview/mock/english/admin.
- **Backend**: FastAPI with modular route layer and service layer.
- **Database**: PostgreSQL (SQLAlchemy ORM + Alembic migrations).
- **Redis**: optional cache layer for LLM response caching (safe fallback supported).
- **AI layer**:
  - LLM calls via `litellm` + Gemini 2.5 Flash
  - RAG via Chroma + sentence-transformers embeddings

---

## 3. FOLDER STRUCTURE

- `backend/routes/`
  - API endpoints only (request validation, auth checks, response shaping).
- `backend/services/`
  - Business logic (`llm_service`, `rag_service`, `mock_service`, `interview_service`).
- `backend/core/`
  - Shared core utilities (configuration, security wrappers).
- `backend/models.py`
  - SQLAlchemy table definitions and relationships.

---

## 4. END-TO-END FLOW

### Interview Flow
1. Name input on setup page.
2. Resume upload.
3. Backend validates file size/content.
4. RAG processing starts in background.
5. Session is created in DB (`interviews` row).
6. Welcome message includes candidate name and interview rules.
7. UI countdown timer starts.
8. Questions generated from LLM (`skill`, `project`, then `followup` pivot).
9. Chat loop sends answers and receives feedback.
10. Session closes with report/summary transition.

### Mock Flow
1. Frontend requests `/api/generate-quiz`.
2. Backend fetches active global mock from DB.
3. Existing mock is returned when present.
4. If force-new is requested, new mock is generated and old one replaced atomically.

### English Flow
1. Topic fetched.
2. Discussion questions generated.
3. User submits responses.
4. Final report generated with fallback-safe scoring.

## 6. DATABASE DESIGN

Key tables:

- `interviews`: interview session state (`session_id`, transcript, status, current_question, candidate_name).
- `global_mocks`: single active mock question set shared across users.
- `rag_status`: persistent RAG processing state (`processing|ready|failed`).
- `cache_entries`: DB cache fallback when Redis is unavailable.

---

## 7. SERVICES EXPLAINED

- `llm_service`
  - All LLM prompting, retries, timeouts, strict schema parsing, fallback responses, cache interactions.
- `rag_service`
  - Resume brief extraction, async embedding, persistent status updates, retry for failed embedding.
- `mock_service`
  - Global mock fetch/create/replace with transaction-safe update path.
- `interview_service`
  - Interview session payload shaping, welcome message, transcript append/state progression.

---

## 8. AI LOGIC

- Questions generated from compact prompt inputs (`resume[:800]`, `jd[:400]`).
- Resume context used for interview personalization.
- Strict JSON schema validation using pydantic models.
- If LLM fails or returns invalid payload:
  - Retry 2-3 times.
  - Return deterministic fallback prompts/questions (for crash-safe UX).

---

## 9. STATE MANAGEMENT

- Session state is persisted in DB (`interviews`), not in-memory.
- RAG progress tracked in DB (`rag_status`) to survive restart.
- Caching hierarchy:
  1. In-process cache
  2. Redis cache (if available)
  3. DB cache fallback (`cache_entries`)

---

## 10. ERROR HANDLING

- Input validation errors return clear API message (`Invalid input`).
- Server-side unhandled errors return safe generic message (`Server error, try again`).
- LLM operations include:
  - timeout
  - retry
  - fallback return payload
- Session checks return `Session expired` when missing/invalid.

---

## 11. PERFORMANCE

- Async background RAG embedding avoids blocking interview start.
- Retry with bounded backoff prevents immediate hard-fail.
- Cache-first LLM response retrieval reduces repeated model calls.
- Resume parsing reduced to focused sections (name/skills/experience) for speed.

---

## 12. SECURITY

- JWT-based auth for user and admin routes.
- Admin login validated from env (`ADMIN_EMAIL`, `ADMIN_PASSWORD`).
- Startup env validation enforces required secrets:
  - `ADMIN_EMAIL`
  - `ADMIN_PASSWORD`
  - `JWT_SECRET_KEY`
- Protected admin routes via role checks.

---

## 13. CRITICAL RISKS

- External LLM provider outages or latency spikes.
- Race conditions around global mock updates (mitigated via DB lock/transaction).
- Missing dependencies or wrong runtime env.
- Redis instability (mitigated with DB cache fallback).

## 14. FUTURE IMPROVEMENTS
